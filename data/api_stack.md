# Stack de la API de catálogo

La aplicación de ejemplo es un backend de catálogo construido en Python. El servicio recibe solicitudes HTTP, valida información de entrada y coordina el acceso a datos. No contiene una interfaz web propia: expone datos consistentes para clientes internos. FastAPI es el framework elegido porque permite declarar rutas, tipos y validaciones de forma clara. Las rutas principales consultan productos, crean pedidos de demostración y muestran el estado operativo del servicio. Cada endpoint devuelve códigos HTTP coherentes y mensajes breves cuando una operación no puede completarse. Las respuestas siguen modelos Pydantic para que el contrato sea previsible.

La estructura separa rutas, servicios y acceso a datos. Las rutas reciben la solicitud y no deben contener consultas SQL extensas. Los servicios aplican reglas de negocio sencillas, por ejemplo validar que una cantidad sea positiva antes de registrar una operación. La capa de datos utiliza SQLAlchemy asíncrono para comunicarse con PostgreSQL. Esta separación permite localizar errores con facilidad y evita que una ruta HTTP conozca detalles de conexiones o transacciones. Las dependencias de FastAPI inyectan una sesión de base de datos cuando una ruta la necesita, y la liberan al terminar la solicitud.

PostgreSQL almacena productos, categorías y pedidos de demostración. Redis se usa exclusivamente como caché de consultas frecuentes del catálogo; no reemplaza la base de datos principal. Cuando un cliente solicita un producto popular, el servicio revisa primero Redis. Si el valor no está disponible, consulta PostgreSQL y guarda una copia con expiración corta. Las operaciones que modifican información siempre escriben en PostgreSQL y, después de confirmar la transacción, invalidan las claves de caché relacionadas. De este modo se evita mostrar un catálogo antiguo después de una actualización y se conserva una fuente de verdad permanente.

La autenticación se resuelve en una dependencia compartida. El cliente envía un token en el encabezado Authorization y la dependencia verifica su formato antes de ejecutar una ruta protegida. El ejemplo no almacena tokens dentro del código ni incluye secretos en estos documentos. Una vez validado el token, la dependencia entrega un identificador de usuario al servicio que lo requiere. Las rutas de consulta pública pueden no exigir autenticación, mientras que las rutas administrativas sí la exigen. Esta distinción se declara explícitamente para que la política de acceso sea visible al revisar cada endpoint.

Pydantic valida los cuerpos de solicitudes y respuestas. Un modelo de creación de producto exige nombre, precio y categoría; un modelo de respuesta define qué campos se devuelven al cliente. La validación ocurre antes de llamar a la capa de servicio. Si el formato es incorrecto, FastAPI responde con un error de validación y no intenta escribir datos incompletos. También se revisan valores de negocio sencillos, como precios no negativos y nombres no vacíos. Esta práctica reduce errores repetidos y facilita a los clientes entender por qué una solicitud fue rechazada.

El manejo de errores es deliberadamente simple. Excepciones de dominio, como un producto inexistente, se transforman en una respuesta 404. Un conflicto de datos, por ejemplo un identificador duplicado, se informa como 409 cuando puede identificarse. Los errores inesperados se registran con contexto técnico y se devuelven al cliente como un mensaje genérico 500 sin revelar detalles internos de PostgreSQL. No se captura una excepción amplia para ocultarla silenciosamente: cada capa registra lo que necesita y permite que el manejador central produzca una respuesta segura.

El logging usa el módulo estándar de Python. Cada solicitud recibe un identificador de correlación que aparece en logs de ruta, servicio y base de datos. Se registran método HTTP, ruta, código de respuesta y duración. No se registran contraseñas, tokens completos ni cuerpos sensibles. Cuando una consulta tarda más de lo esperado, el log incluye el nombre de la operación para facilitar el diagnóstico. Esta información se relaciona con las métricas del documento de monitoreo, en especial latencia y tasa de errores. Los mensajes de error incluyen trazas internas solo en el entorno de desarrollo.

La configuración vive en variables de entorno cargadas al inicio del programa. El proyecto define proveedor de LLM, modelo, temperatura, tamaño máximo de respuesta, modelo de embeddings, directorio de Chroma y cantidad de fragmentos recuperados. Los valores de ejemplo están en `.env.example`, mientras que `.env` no se versiona. La URL de PostgreSQL y la dirección de Redis seguirían el mismo principio en una ejecución real. Centralizar la configuración evita leer variables repetidamente en cada función y permite cambiar entornos sin modificar archivos Python.

La comunicación con la base de datos es asíncrona. Una ruta espera la operación de SQLAlchemy mediante `await`, por lo que no bloquea el event loop mientras PostgreSQL responde. Las sesiones se cierran al finalizar la solicitud y las transacciones se confirman solo después de que la operación completa fue validada. Si ocurre un error durante una escritura, la capa de datos realiza rollback antes de liberar la sesión. Redis también se consulta con un cliente compatible con el flujo asíncrono para que una búsqueda de caché no detenga otras solicitudes. La API mantiene límites razonables de tiempo para evitar esperar indefinidamente.

Entre las buenas prácticas están usar nombres claros, funciones pequeñas y pruebas unitarias sin servicios externos. Los endpoints no crean conexiones manualmente; reciben dependencias configuradas. Las respuestas incluyen solo campos necesarios y los logs no imprimen secretos. Las migraciones de esquema se ejecutan fuera del arranque de la API para evitar cambios inesperados al escalar instancias. El objetivo del dataset es describir una arquitectura backend consistente: FastAPI coordina solicitudes, PostgreSQL mantiene información permanente, Redis acelera lecturas frecuentes y la observabilidad permite detectar problemas antes de afectar a usuarios.
