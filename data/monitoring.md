# Monitoreo técnico y observabilidad

El servicio de catálogo se observa mediante métricas, logs y health checks. El objetivo no es registrar cada detalle posible, sino disponer de señales suficientes para saber si la API está disponible, si responde con rapidez y si mantiene una comunicación saludable con PostgreSQL y Redis. La observabilidad permite relacionar una solicitud lenta con una consulta lenta, una conexión agotada o un aumento de errores HTTP. Cada señal tiene una finalidad práctica: detectar problemas, medir su impacto y guiar un diagnóstico ordenado.

Las métricas principales de la API son volumen de solicitudes, latencia, códigos de respuesta y tasa de errores. El volumen indica cuántas solicitudes llegan por ruta durante un intervalo. La latencia se mide como tiempo total desde que ingresa una petición hasta que se envía la respuesta. Se observan promedio, percentiles y valores máximos, porque un promedio bajo puede ocultar algunas respuestas muy lentas. Los códigos 2xx indican operaciones exitosas, los 4xx muestran solicitudes inválidas o no autorizadas y los 5xx requieren investigación del servidor.

Una alerta se genera cuando la latencia promedio supera 500 ms durante cinco minutos consecutivos. Esta regla evita notificaciones por un pico aislado y permite reaccionar cuando el problema persiste. La alerta contiene la ruta afectada, el período evaluado y el identificador del entorno. El equipo revisa entonces si la demora proviene de PostgreSQL, Redis, validación de entrada o una dependencia interna. También se puede configurar una alerta para un aumento sostenido de errores 5xx, porque una API disponible pero incapaz de completar operaciones sigue siendo un incidente relevante.

Los logs estructurados complementan las métricas. Cada solicitud genera un evento con identificador de correlación, método HTTP, ruta, código de respuesta y duración. Los servicios internos usan el mismo identificador al registrar operaciones de caché o base de datos. Así se puede seguir una solicitud completa sin buscar por hora y texto libre. Los logs de error incluyen el nombre de la operación y una descripción técnica suficiente para desarrollo, pero no incluyen tokens, contraseñas ni información sensible. En producción se limita el detalle que llega al cliente.

Los health checks tienen dos niveles. Un check básico confirma que el proceso HTTP está vivo y puede responder una ruta simple. Un check de disponibilidad verifica además que la aplicación puede obtener una conexión de PostgreSQL y ejecutar una consulta pequeña como `SELECT 1`. Redis puede verificarse con una operación de lectura ligera. Estos checks no deben ejecutar reportes costosos ni recorrer tablas completas. Un resultado fallido se registra y permite que un sistema externo retire temporalmente una instancia que no está lista para recibir tráfico.

El monitoreo de base de datos registra conexiones activas, conexiones esperando, tiempo de adquisición del pool, duración de consultas y errores de transacción. El pool tiene un máximo de 20 conexiones; por eso es importante detectar si muchas solicitudes esperan una conexión libre. Una cola creciente puede indicar consultas lentas, sesiones que no se liberan o una carga mayor a la esperada. La métrica no debe interpretarse sola: se compara con latencia de rutas y con el tipo de consulta. Un aumento breve durante una tarea programada puede ser normal, mientras que una saturación continua necesita análisis.

Redis se monitorea como caché, no como fuente permanente de información. Se mide tasa de aciertos, tasa de fallos, tiempo de respuesta y errores de conexión. Una caída de aciertos puede aumentar consultas hacia PostgreSQL y elevar la latencia de rutas de catálogo. Sin embargo, una respuesta desde caché no debe ocultar datos antiguos: las claves relacionadas se invalidan después de confirmar cambios en PostgreSQL. Los logs indican cuándo una operación usó caché o realizó lectura persistente, lo que facilita explicar diferencias de rendimiento entre solicitudes similares.

La disponibilidad se calcula observando health checks y respuestas correctas durante un período. No basta con que un proceso esté ejecutándose: debe poder atender solicitudes relevantes dentro de los límites acordados. Las métricas se presentan en paneles sencillos para ver tráfico, errores, latencia y estado de dependencias en una misma pantalla. Los paneles no sustituyen alertas; sirven para investigar una alerta o revisar tendencias. Un aumento gradual de latencia puede revelar un problema antes de que se alcance el umbral de 500 ms.

El troubleshooting comienza por confirmar el alcance. Si una sola ruta falla, se revisan sus logs y dependencias directas. Si todas las rutas tienen latencia alta, se revisan recursos de la instancia, conexiones de PostgreSQL y disponibilidad de Redis. Si aparecen errores 5xx, se agrupan por tipo de excepción y ruta. Luego se compara el inicio del incidente con cambios de configuración, despliegues o aumentos de tráfico. El identificador de correlación permite pasar desde una métrica agregada a ejemplos concretos sin exponer información privada.

Las buenas prácticas de observabilidad incluyen definir umbrales comprensibles, probar alertas y documentar cómo responder a cada señal. Un equipo debe saber quién revisa una alerta, qué panel consultar y cuándo escalar el problema. Los logs se retienen el tiempo necesario para diagnóstico y se protegen de datos sensibles. Las métricas se revisan después de incidentes para ajustar límites realistas. Este dataset no incluye información sobre proveedores de pagos: cuando una pregunta requiere un dato ausente, el sistema RAG debe responder que no lo sabe en lugar de inventar una respuesta.
