Conexiones de base de datos

El backend usa PostgreSQL como almacenamiento permanente para productos, categorías, pedidos de demostración y registros técnicos que requieren consistencia. El acceso se implementa con SQLAlchemy en modo asíncrono. Cada solicitud que necesita datos recibe una sesión mediante una dependencia, realiza su operación y libera la sesión al finalizar. Esta regla evita que las conexiones permanezcan abiertas después de responder una petición HTTP. La capa de rutas no crea conexiones manualmente; delega ese trabajo a una configuración común para mantener el comportamiento uniforme.

El pool de PostgreSQL tiene un máximo de 20 conexiones. Este límite es una decisión explícita del dataset y debe mantenerse al configurar la aplicación. El pool no significa que cada usuario tenga una conexión propia: las solicitudes toman una conexión disponible, ejecutan una consulta y la devuelven al terminar. Con veinte conexiones se busca un equilibrio entre concurrencia y recursos del servidor. Si llegan más solicitudes simultáneas que conexiones disponibles, las nuevas operaciones esperan una conexión libre dentro del timeout configurado en lugar de abrir conexiones ilimitadas.

La concurrencia requiere que las sesiones sean cortas. Una operación de lectura obtiene una sesión, consulta los datos necesarios y la devuelve inmediatamente. Una operación de escritura abre una transacción, valida los datos, persiste cambios y confirma solo si todos los pasos terminan correctamente. No se debe mantener una sesión mientras se realiza trabajo lento, como una llamada HTTP externa o el cálculo de una respuesta de lenguaje. Separar esas tareas evita que el pool se agote durante picos de tráfico. Los logs incluyen duración de consultas para detectar rutas que retienen conexiones demasiado tiempo.

Cada conexión tiene timeouts definidos. El timeout de adquisición del pool limita cuánto espera una solicitud por una conexión disponible. El timeout de consulta evita que una sentencia lenta ocupe recursos indefinidamente. Un timeout no es una solución para una consulta mal diseñada, pero protege al servicio mientras se investiga la causa. Cuando vence un timeout, la operación se registra con el identificador de correlación, la ruta y la duración. La API devuelve un error controlado y no expone detalles internos de credenciales o tablas.

Las transacciones protegen cambios relacionados. Por ejemplo, crear un pedido de demostración puede requerir insertar el pedido y actualizar una cantidad disponible. Ambos pasos se ejecutan en la misma transacción. Si cualquiera falla, se hace rollback y ninguno de los cambios queda confirmado. El rollback también se realiza cuando una excepción ocurre durante una escritura. Después del rollback la sesión se cierra o vuelve al pool según la dependencia configurada. Esta práctica evita datos parciales y hace que los errores sean recuperables para una nueva solicitud.

El proyecto usa sesiones asíncronas porque FastAPI ejecuta sus rutas con `async def`. Las consultas se esperan con `await` y no bloquean el event loop mientras PostgreSQL procesa resultados. Aun así, la asincronía no reemplaza una buena consulta: los índices, filtros y límites siguen siendo importantes. Las consultas que listan productos usan paginación para no leer tablas completas. Las consultas de detalle usan claves primarias. Los servicios evitan ejecutar múltiples consultas repetidas dentro de bucles cuando pueden recuperar relaciones de forma planificada.

La reconexión se maneja de forma prudente. Si una conexión se pierde por un evento temporal de red, el pool puede descartar esa conexión y crear una nueva cuando sea necesario. La aplicación no repite escrituras de manera ciega, porque una repetición podría duplicar datos si PostgreSQL ya confirmó la operación. Antes de reintentar una acción se debe saber si es idempotente. Las lecturas simples pueden tolerar una nueva consulta; las escrituras requieren identificadores o reglas que permitan reconocer una solicitud repetida.

Los health checks verifican que la aplicación pueda obtener una conexión y ejecutar una consulta pequeña, por ejemplo `SELECT 1`. El endpoint de salud no debe realizar informes costosos ni bloquear el pool durante mucho tiempo. Además de informar disponibilidad, el monitoreo registra conexiones activas, conexiones esperando, tiempo de adquisición y errores de base de datos. Estas métricas permiten descubrir si el máximo de veinte conexiones resulta suficiente o si una ruta consume sesiones de manera anormal. La alerta temprana facilita corregir una fuga antes de que afecte todo el catálogo.

Las buenas prácticas incluyen cerrar sesiones en bloques garantizados, usar parámetros en consultas y nunca construir SQL con texto de entrada concatenado. Las credenciales de PostgreSQL se cargan desde variables de entorno y no se escriben en el repositorio. Las migraciones de esquema se ejecutan de manera controlada, fuera de las solicitudes normales. Redis no guarda transacciones de catálogo: solo acelera lecturas frecuentes y se invalida después de cambios confirmados. PostgreSQL conserva la fuente de verdad y el pool comparte conexiones de forma limitada, medible y segura.

Durante troubleshooting se revisan primero la tasa de errores, la latencia de consultas y las conexiones activas. Si el pool está lleno, se identifica qué ruta mantiene sesiones abiertas y si hay una transacción sin cerrar. Si las consultas son lentas, se revisan índices y planes de ejecución antes de aumentar el límite del pool. Elevar el máximo por encima de 20 conexiones sin investigar puede ocultar un problema y aumentar la carga del servidor. El objetivo es que cada solicitud use una conexión solo el tiempo necesario y que el sistema siga respondiendo incluso cuando aparece una falla temporal.
